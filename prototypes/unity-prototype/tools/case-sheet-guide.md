# 케이스 시트 작업 가이드 (마왕성 인사팀)

> 지원자 케이스를 **구글 시트에서 저작 → 게임에 반영**하는 방법.
> 도구: [cases_sheet.py](cases_sheet.py) · 대상 데이터: `Assets/StreamingAssets/MawangHR/gamedata.json`
> 작성: 2026-07-04 (S2c 기준, 케이스 17건)

## 0. 큰 그림

```text
구글 시트 (진실 원본)          이 저장소                      게임
┌──────────────┐   CSV 다운로드   ┌─────────────┐   Play   ┌────────┐
│ 케이스 표 편집 │ ───────────────→ │ import 명령  │ ───────→ │ 풀 뽑기 │
│ (브라우저)    │                  │ 검증+백업+반영 │          │        │
└──────────────┘                  └─────────────┘          └────────┘
```

**철칙: 시트 작업을 시작한 순간부터 지원자 데이터의 진실 원본 = 시트다.**
gamedata.json의 `applicants`를 손으로 고치지 말 것 — 다음 import 때 덮어써진다.
(공문 directive·스케줄링 블록·jds는 여전히 JSON 담당. 변환기가 건드리지 않는다.)

> 참고: 시트 관리 대상은 **서류 심사 케이스(`applicants`)뿐**이다.
> 면접 지원자(`interviewees` — 답변 4종 포함)·질문 카드(`cards`)는 구조가 달라 JSON 직접 관리.
> 면접 케이스가 늘어나면 그때 시트 두 번째 탭으로 확장한다.

## 1. 최초 1회 설정 (약 15분)

1. **CSV 준비**: 터미널에서
   ```
   python3 prototypes/unity-prototype/tools/cases_sheet.py export
   ```
   → `tools/cases.csv` 생성 (현재 게임 데이터 전체).
2. **시트 생성**: 브라우저에서 `sheets.new` → **파일 > 가져오기 > 업로드** → cases.csv → "현재 시트 바꾸기".
3. **보기 설정**:
   - 보기 > 고정 > **1행** (헤더 고정)
   - 전체 선택 → 서식 > 줄바꿈 > **줄바꿈** (긴 텍스트 접기)
   - 열 너비: id·정답은 좁게, 이력·해설은 넓게
4. **실수 방지 장치 (드롭다운)** — 데이터 > 데이터 확인 > 규칙 추가:
   - **정답** 열: `PASS`, `FAIL`
   - **직무** 열: `adm`, `guard` (JD가 늘면 여기도 추가)
   - **풀** 열: `day1`, `day2`, `day3`
5. **조건부 서식** — 서식 > 조건부 서식:
   - 정답 열 "텍스트가 정확히 일치: FAIL" → 빨간 배경 / "PASS" → 초록 배경
   - → 정답 분포가 한눈에 보임 (목표 감각: 명백합 20% / 명백불 20% / 간파 50% / 함정 10%)
6. **필터** — 데이터 > 필터 만들기 → 직무별·정답별·풀별로 걸러 보기.

## 2. 일상 작업 루틴

1. 시트에서 수정/추가 (자동 저장됨)
2. **파일 > 다운로드 > 쉼표로 구분된 값(.csv)**
3. 터미널에서 반영 (Claude에게 "이 파일 반영해줘"라고 해도 됨):
   ```
   python3 prototypes/unity-prototype/tools/cases_sheet.py import ~/Downloads/받은파일.csv
   ```
   - 규칙 위반 시: **몇 행의 무엇이 잘못됐는지** 출력하고 반영 중단 (JSON 무사)
   - 통과 시: 반영 + 직전본 `gamedata.json.bak` 자동 백업
4. 유니티 **Play**로 확인 (시작 화면에 에러가 뜨면 데이터 문제)
5. 확인되면 커밋 (gamedata.json이 저장소에 남는 기록)

## 3. 열 사전 (규칙 포함)

| 열 | 의미 | 규칙 |
|----|------|------|
| **id** | 케이스 고유 키 (로마자) | ⚠️ **한 번 정하면 절대 바꾸지 말 것** — 셔플백(본 케이스 기억), 첫 슬롯 고정(firstId), 나중엔 초상화 파일명까지 이 키에 묶인다. 중복 금지 |
| 이름 | 게임에 표시되는 이름 | 자유 |
| 종족 | 표시용 텍스트 (예: "고블린 ♂") | 자유 — §5의 종족ID와 다름에 주의 |
| 직무 | 지원한 JD의 id | `adm` / `guard` (JD 추가 시 gamedata.json의 jds에도 추가) |
| 연봉 | 표시용 (개그 포인트) | 자유 |
| 한마디 | 이력서 상단 어필 문구 | 자유 |
| 이력1~3 | 클릭 가능한 단서 줄 | **1~3줄** (4줄부터 레이아웃상 특이사항과 겹침). 이력2·3은 비워도 됨 |
| 근거1~3 | 해당 줄이 결정적 근거인가 | **빈칸**(단서 아님) 또는 **정답과 같은 값**만. 예: 정답이 FAIL이면 근거 칸은 빈칸 아니면 FAIL |
| 특이사항 | 인사팀 메모 (이것도 단서) | 자유 |
| 특이근거 | 특이사항의 근거 여부 | 근거1~3과 같은 규칙 |
| 정답 | 이 케이스의 정답 | `PASS` / `FAIL` |
| 해설 | 결산 화면의 인사팀장 총평 | "왜 이게 정답인지 + 코미디 한 줄" 구조 권장 |
| 풀 | 등장하는 날 | `day1` / `day2` / `day3` (지금은 day1만 사용) |

**케이스 1건의 필수 조건**: 정답 방향 근거(이력 근거 또는 특이근거)가 **최소 1개** — 없으면 플레이어가 근거 채점에서 절대 적중할 수 없는 케이스가 되므로 변환기가 거부한다.

### 좋은 케이스 감각 (기존 17건에서 뽑은 패턴)

- **한 줄 훅**이 있어야 한다: "감자 도장", "손이 통과함", "다람쥐가 노려봐서" — 단서이자 개그.
- 반전축을 다양하게: 착함=결격(물컹이) / 서툰 위조(블라드) / 직무 미스매치(불장난) / 겉면≠실체(쿠키할멈).
- 해설은 **판단 원칙을 한 문장으로** 남긴다 ("직무가 다르면 정답도 다르다") — 학습 모먼트가 됨.

## 4. 자주 나는 에러와 대처

| 에러 메시지 | 원인 | 대처 |
|------------|------|------|
| `정답은 PASS/FAIL이어야` | 드롭다운 없이 직접 입력하다 오타 | 드롭다운 설정(§1-4) |
| `근거N은 빈칸 또는 정답과 같아야` | 정답 FAIL인데 근거에 PASS 기입 | 근거는 "정답 방향의 결정적 단서" 표시임 — 방향이 다르면 빈칸 |
| `결정적 근거가 하나도 없습니다` | 근거 칸을 전부 비움 | 최소 1개 지정 |
| `이력N이 비었는데 근거N만 있음` | 행 밀림 (열 하나 어긋남) | 해당 행 열 정렬 확인 |
| `id 중복` | 복사-붙여넣기 후 id 안 바꿈 | 새 id 부여 |

## 5. 캐릭터 비주얼 분류 설계 (3D 모델·초상화를 붙일 때) ⭐

**방향 확정 (2026-07-04): 종족을 통폐합하지 않는다 — 종족별 복셀 모델을 최대한 만든다** (S2c 기준 16종).
복셀은 개당 제작 부담이 작아 가능한 방향. 대신 아래 3층 분류 + 폴백 규약으로 리스크를 없앤다:

```text
캐릭터 비주얼 = 종족ID (모델)  +  변형 (부착물·파라미터)  +  초상화 (케이스 고유)
                 종족당 1개 목표      모자·안경 등 스왑           id당 1장
```

### 5a. 3층의 역할

| 층 | 키 | 무엇을 결정 | 예 |
|----|----|-----------|---|
| **종족ID** | `speciesId` (기계용 로마자) | 복셀 3D 모델·리액션 애니 세트 | `goblin`, `slime`, `skeleton`, `orc`, `vampire`, `witch` |
| **변형** | `variant` (자유 태그) | 같은 모델의 개성 — **부착물(모자·안경·망토·손에 든 물건)**, 색상, 크기 배율. 부착물은 별도 복셀 조각으로 만들어 앵커(머리·눈·손)에 붙임 → 종족 간 재사용 가능 | 뻥볼린 = `goblin` + `potato_stamp`(감자도장 소품) |
| **초상화** | 파일명 규약 = **케이스 id** | 서류/스케줄링 사진 카드 1장 | `mulkeong.png`, `kukihalmi.png` |

**핵심 원칙 1 — 표시용과 기계용을 분리한다.** 시트의 "종족" 열("고블린 ♂")은 플레이어가 읽는 텍스트고, `speciesId`는 에셋을 찾는 키다. 절대 한 칸에 겸용하지 말 것 (텍스트를 다듬는 순간 모델 링크가 끊긴다).

**핵심 원칙 2 — 초상화는 규약으로, 예외만 기입.** 파일명을 `초상화/{id}.png`로 통일하면 시트에 열을 추가할 필요가 없다. 예외(둘이 같은 그림을 공유 등)가 생길 때만 `초상화` 열을 추가해 예외만 적는다.

**핵심 원칙 3 — id는 영원하다.** 초상화 파일명·셔플백·firstId가 전부 id에 묶이므로, 케이스 이름(한글)은 마음껏 바꿔도 id는 바꾸지 않는다.

### 5b. 시트에 추가될 열 (아트 착수 시점에)

```text
| 종족ID   | 변형            |
| goblin  | potato_stamp   |   ← 뻥볼린
| goblin  |                |   ← 그볼린 (기본형)
| slime   |                |   ← 물컹이
```

- 드롭다운으로 `speciesId` 목록 관리 (오타 방지 + 현재 종족 수를 한눈에 파악).
- **폴백 규약 ⭐**: 아직 모델이 없는 종족은 `placeholder`(기본 복셀 몸통 + 종족 색)로 자동 대체 — 모델이 전부 완성되기 전에도 게임은 항상 완주 가능. 제작 우선순위 = 풀 등장 빈도 → 개그 밀도 순.
- 변형(부착물)의 역할 = **케이스 증산**: 새 케이스를 쓸 때 기존 종족 모델 + 새 모자/안경이면 아트 비용이 거의 0이다. (모델 수 절약용이 아님 — 종족은 최대 제작 방향)

### 5c. 에셋 폴더 규약 (제안)

```text
프로토 단계:  Assets/MawangHR/Portraits/{id}.png        ← 초상화 (케이스당 1장)
             Assets/MawangHR/Models/{speciesId}.prefab  ← 복셀 모델 (종족당 1개)
프로덕션:    Addressables 키 = "portrait/{id}", "monster/{speciesId}"  (기술 스택 규정)
```

변환기(cases_sheet.py)는 이 열들이 추가되면 함께 확장한다 — 그 시점에 Claude에게 "종족ID 열 추가해줘"라고 요청하면 됨.
